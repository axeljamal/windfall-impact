# Windfall Impact

A public dashboard of the Windfall pilot's numbers. [Windfall](https://windfall.marea-dvipa.uk) turns surplus food into small hosted suppers for three to eight neighbours, piloting in Brighton & Hove. This site shows what that adds up to: suppers and venue tables listed, chairs offered and filled, neighbourhoods, where the surplus comes from, how people chip in, host ratings and one neighbour's supper history.

Two pages:

- `/` the dashboard: eight headline numbers, six charts and a table of the food being rescued.
- `/method` how each number is made, what isn't counted yet, and why.

Built with Next.js 16 (App Router, server components), TypeScript, Tailwind CSS 4 and hand-drawn SVG charts (no chart library). Every chart has a title, a one-line text summary, keyboard-focusable marks with tooltips, and a button that shows its numbers as a table. Animations only run when the browser has not asked for reduced motion. Colours, type and tone follow the Windfall app's `DESIGN.md` and `src/theme.ts`, in day and night schemes; `src/lib/contrast.test.ts` checks every text pair at 4.5:1 and every chart mark at 3:1.

## Where the data comes from

**Sample data from the pilot demo.** Windfall has no live aggregate source yet, so the numbers are counted from the records the Windfall app ships for its demo mode (the one at [demo.marea-dvipa.uk](https://demo.marea-dvipa.uk)). They are copied by hand, value for value, into [`src/data/sample.ts`](src/data/sample.ts), from Windfall commit `f36dd81`:

| In `sample.ts` | Copied from (Windfall repo) |
| --- | --- |
| `HOME_SUPPERS` | `SUPPERS` in `src/data.ts` (host supper counts and ratings from each `hostSub` line) |
| `VENUE_TABLES` | `DEMO_SLOTS` in `src/lib/tables.ts` (start times left out: they are relative to "now") |
| `SOURCES` | `SOURCES` in `src/data.ts` |
| `LEDGER` | `LEDGER` in `src/data.ts`, joined with `DEMO_PAST` in `src/lib/history.ts` |
| `PARTNER_VENUES` | `VENUES` in `src/data.ts` |
| `GUEST_REQUESTS` | `GUEST_REQUESTS` in `src/data.ts` |

Hand-copied rather than generated by a script, so the build never depends on the Windfall repo being next to it. When Windfall's demo data changes, update `sample.ts` and the expected values in `src/lib/impact.test.ts` together.

Nothing is invented. Where Windfall gives words ("a glut of", "two crates of"), the words are shown and nothing is summed. Neighbours fed, kilos saved and return rates over time are listed as not counted yet.

## Swapping in live data

Every page reads one typed function, `getImpact(): Impact` in [`src/lib/impact.ts`](src/lib/impact.ts). To go live, replace its body with a call to a Supabase aggregate (for example an RPC returning counts per neighbourhood, chairs taken and offered, and source shares) and map the result onto the same `Impact` type. Because the site is a static export, that call runs at build time: make `getImpact` async, `await` it in the two pages, and rebuild on a schedule (or after each supper) to refresh the numbers. The aggregate should only ever return counts across many suppers, never names or individual tables.

## Run and build

```sh
npm install        # once
npm run dev        # http://localhost:3101
npm test           # Vitest: metric functions and colour contrast
npm run lint
npm run build      # static export to out/
npm run serve      # serve out/ on http://localhost:3101
```

`wrangler.jsonc` is ready for Cloudflare Workers static assets (name `windfall-impact`, assets from `out/`). It has not been deployed; `npx wrangler deploy` after a build would do it.

## Why a Next.js static export

The numbers change when suppers happen, not when someone opens the page, so there is nothing to compute per request: a static export lets Next.js render every chart, summary and data table to HTML at build time, using server components that ship no JavaScript, and serve it as plain files from Cloudflare's edge with no server to run or secure. A client-only SPA would send the data and chart code to every visitor and draw the page in their browser, so the first view is a blank shell, screen readers and search engines wait on JavaScript, and phones on a weak signal pay for it. Here only the small interactive parts (the neighbourhood filter, tooltips, table toggles and the day/night switch) are client components, and the static export keeps a clear path to build-time live data later.
